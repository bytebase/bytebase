# Manage the Bytebase Cloud Sample Project Instance lifecycle

Bytebase Cloud needs a one-click database for product evaluation without requiring users to bring infrastructure. Cloud SQL provides only a restricted `postgres` administrator, while users need to own seeded application objects to exercise later DDL, and PostgreSQL does not provide a dependable database creation timestamp from which to derive expiration.

A **Sample Project Instance** is the temporary-evaluation aggregate prepared for one selected Project: one Bytebase Project Instance plus one dedicated database and non-superuser login role on Bytebase's shared, dedicated Cloud SQL PostgreSQL instance. Each Workspace receives one lifetime entitlement to prepare this aggregate. The aggregate is prepared synchronously so it is ready for use when returned.

The Cloud SQL control-plane user owns each physical database so it can reliably remove it, while the sample role owns every seeded and subsequently created application object. A new database denies connections until Bytebase has revoked default `PUBLIC` access and granted access to its dedicated role. Bytebase seeds directly as that role rather than cloning a template because cloned objects retain the template owner's identity, which the restricted administrator cannot reliably transfer.

An independent control-plane record without foreign keys preserves the single-use Workspace entitlement, persisted random instance ID, and its derived database and role names without depending on ordinary Workspace, Project, Project Instance, or Database lifecycle records. The random instance ID deterministically derives the persisted names in the `bb_sample_*` namespace. That namespace and every reserved instance, database, and role name belong exclusively to this reservation, including when its entitlement record is retained after cleanup. Pending records also store their owning replica. Lifecycle state is derived solely from `created_at`, `expires_at`, and `deleted_at`; seven-day eligibility is immutable and begins only after provisioning and seeding, Project Instance registration, and initial Database discovery all succeed.

The Manager owns provisioning compensation and cleanup. It reserves and commits ownership before external work; it never holds a metadata transaction while provisioning or compensating. A pending attempt may be claimed only after its three-minute lifecycle window has elapsed. A different replica additionally requires the previous owner's heartbeat to be missing or stale for one minute; the same replica may retry its own expired attempt. A successful claim starts a fresh three-minute lifecycle window, so time spent waiting for the previous attempt does not consume the new owner's provisioning and compensation budget. Every activation and pending deletion is fenced by Workspace, instance ID, and replica ID, so a superseded worker cannot finalize. An internal runner performs cleanup at startup and then hourly on every replica. It scans eligible records in Workspace order, claims one record at a time with `FOR UPDATE SKIP LOCKED` and a Workspace cursor, and commits each physical cleanup attempt before moving to the next record. This limits each external attempt to its own row lock while allowing failed records to remain eligible later. Pending rows survive a cleanup failure or process crash, so a later Manager attempt can compensate using the reservation's deterministically derived names. Cleanup removes only the physical Cloud SQL databases and roles and retains Workspace, Project, Project Instance, and Database metadata. The entitlement remains consumed after cleanup; the design provides neither an entitlement reset nor a separate user-visible expired state.

We rejected asynchronous preparation because the shared infrastructure is already provisioned and measured role creation, database creation, direct seeding, and Database discovery fit within a bounded request. We also rejected user ownership of the database because PostgreSQL reserves database deletion for its owner or a true superuser, which Cloud SQL does not provide to customers.

Operational requirements are in [Sample Project Instance operations](../operations/sample-project-instance.md). Detailed API, configuration, persistence, concurrency, recovery, cleanup, testing, and scope decisions are specified in [BOT-58](https://linear.app/bytebase/issue/BOT-58).
